# graduate
选题简介：基于“人机协同”的高校教务智能咨询平台
1. 项目名称 基于大语言模型与人机协同机制的高校教务咨询系统设计与实现

2. 核心痛点
学生端： 传统的教务系统（如URP）操作复杂，政策文件晦涩难懂，学生找不到答案。
管理端： 教务老师每天重复回答大量同质化问题，效率低；纯 AI 客服（Chatbot）容易产生“幻觉”，在学分、选课等严肃问题上不可靠。

3. 解决方案（核心创新点） 本项目提出一种**“AI 挡在前面，老师守在后面”**的协同模式：
第一层（AI 自动解答）： 接入定制化的 Agent，基于校园知识库自动回答 80% 的常见问题。
第二层（人工兜底机制）： 当学生对 AI 回答不满意时，一键生成“待处理工单”流转至后台。
第三层（知识闭环）： 老师的回复不仅解决了当前问题，还将作为新数据反哺给 AI，让它越来越聪明。

4. 技术路线
前端： Vue 3 + Element Plus（响应式交互界面）
后端： Spring Boot + MyBatis Plus（业务逻辑与数据处理）
大模型： 接入 Agent API（如 Coze/Dify 发布的应用接口）
数据库： MySQL 8.0（存储用户、对话日志及工单数据）

读书实践周推进：代码修改、论文写作

1. 实践周完成内容说明
本周实践活动主要围绕“毕业设计深度推进”与“职业能力进阶/创业项目运营”两个维度展开：
毕业设计推进：

专业学习与创业实践（AI产品经理维度）：

2. 重点工作详细过程说明：RAG咨询系统检索精度优化
为了提升毕业设计中教务咨询系统的回答准确度，本周重点对检索链路进行了重构：
数据清洗与分块（Chunking）： 针对冗长的教务处政策文件，放弃了等长切割，改用基于语义段落的递归字符分割器（RecursiveCharacterTextSplitter），确保每个知识块的完整性。
向量库构建： 采用开源向量数据库进行本地部署，将清洗后的教务数据转化为Embedding向量。
多路召回策略： 引入了“向量检索+关键词检索（BM25）”的双路召回机制。针对特定名词（如“绩点计算”、“缓考申请”）使用关键词增强，弥补向量检索在特定术语上的模糊性。
Rerank重排序： 在检索结果反馈给LLM之前，加入了一个轻量级的Reranker模型，对Top-10的结果进行相关度精排，过滤掉干扰信息。

3. 遇到的问题及解决方法
问题一：RAG系统产生“幻觉”导致政策误解读
现象： 当用户询问不存在的教务政策时，系统会基于Embedding的相似度编造答案。
解决方法： 在Prompt中加入严格的限制条件（“如果提供的背景资料中没有相关信息，请直接回答‘暂未查询到相关规定’，禁止自行发挥”），并引入Score门槛值，低于0.7分的相关度结果不予采纳。

问题二：创业项目社群管理中的恶意用户攻击
现象： 发现个别用户通过反复注销旧账号、注册新账号的方式绕过黑名单机制，试图进入种子用户群。
解决方法： 从产品逻辑层面增加了针对同一设备ID和IP地址的注册频率限制，并引入了基于NFC物理设备验证的实名准入机制，大幅提高了恶意注册的门槛。

4. 实践总结
本次实践周是我从学术校园向职业场域过渡的关键阶段。通过一周的密集实践，我不仅在技术执行力上有所提升，更在思维方式上完成了从“功能实现”到“价值交付”的转变。
在专业技术层面， 毕业设计的RAG系统开发让我深刻意识到，AI产品的核心竞争力不在于调用API的繁琐程度，而在于对底层数据分布的深刻理解和对中间件逻辑的精细调优。通过将SpringBoot、Vue与AI框架相结合，我更清晰地看到了全栈开发能力对一个B端产品经理的重要性——只有懂实现原理，才能在PRD撰写中准确评估技术边界。

在职业心态层面， 无论是实习中的B端AI外呼系统优化，还是创业项目中的风控逻辑设计，都让我体察到现实商业环境的复杂性。现实中的用户并非总是理想化的，对抗性攻击和极端边界情况是产品经理必须面对的常态。这要求我们在设计产品逻辑时，必须具备严密的逻辑思维和对效率的极致追求。

在社会价值层面， 我的毕设论文聚焦于数字金融对消费差距的影响，这让我始终保持一种“理想主义”的视角。我意识到，无论是开发一个咨询系统，还是运营一个文化衍生品，其终极目标应当是利用技术手段解决信息不对称问题，创造真实的社会价值。
